# PhotoRental (Java)
Сервис по аренде фото и видео-оборудования (в том числе и расходников, таких как аккумуляторы и SD карты).

Приложение позволяет клиентам арендовать фото и видеотехнику на различный срок. Данные хранятся в PostgreSQL, управление идёт через REST API, описание API доступно в Swagger UI.

## Функционал
Для различных пользователей функционал разный, так как приложение рассчитано как на клиентов, так и на сотрудников.

### Для клиента:
- Возможность арендовать оборудование на определённый срок (начало брони не может быть в прошлом)
- Продлить время аренды, если именно на эту позицию нет чужой брони (у кого бронь раньше, тот в приоритете)
- Отменить бронь, пока технику не выдали
- При аренде старается подбираться наилучшее оборудование, доступное прямо сейчас на складе

### Для менеджера:
- Возможность выдать/принять оборудование у клиентов
- Изменять состояние техники и оставлять заметки (причина обязательна, всё попадает в журнал)

### Для администратора:
- Все возможности менеджера
- Возможность управлять пользователями, моделями и каталогом техники
- Возможность списывать оборудование со склада, если оно не подлежит ремонту (тоже с обоснованием причины). Технику с незавершёнными арендами списать нельзя, списанную технику восстановить нельзя

## Технологии
Java 21, Spring Boot 4, Spring Data JPA, PostgreSQL, Maven, Lombok, springdoc (Swagger UI), JUnit 5 и Mockito.

## База данных
Схема лежит в `db/schema.sql`: категории, модели и экземпляры техники, пользователи (одна таблица для всех ролей), аренды и заметки о состоянии. Схема приведена к BCNF: общие данные модели (бренд, название, тариф) вынесены из экземпляров техники.

Часть правил защищена самой базой:
- нельзя создать две пересекающиеся по датам аренды одной техники (ограничение `EXCLUDE` на диапазон дат);
- списанная техника всегда в статусе `RETIRED` и наоборот;
- логин и почта уникальны без учёта регистра;
- серийные номера (`CAM-00001`) выдаются по счётчику категории.

Hibernate только проверяет схему (`ddl-auto=validate`), таблицы он не создаёт.

## Запуск
1. Создать базу и пользователя, затем выполнить `db/schema.sql` в созданной базе (например, в DBeaver целиком, через «Execute script»):
```
CREATE USER photorental WITH PASSWORD '...';
CREATE DATABASE photorental OWNER photorental;
```
2. Задать подключение через переменные окружения (пароль в репозиторий не попадает):
```
export DB_URL=jdbc:postgresql://localhost:5432/photorental
export DB_USER=photorental
export DB_PASSWORD=...
```
3. Запустить приложение:
```
./mvnw spring-boot:run
```
После запуска:
- Swagger UI: http://localhost:8080/swagger-ui.html
- описание API в JSON: http://localhost:8080/v3/api-docs

## REST API
Все методы сгруппированы в Swagger UI по разделам. Ошибки возвращаются в формате ProblemDetail: `400` — неверный запрос, `404` — объект не найден, `409` — нарушено бизнес-правило или ограничение БД.

| Раздел | Метод и путь | Что делает |
|---|---|---|
| Категории | `GET /api/categories` | список категорий |
| Пользователи | `GET /api/users?role=` | список, можно отфильтровать по роли |
| | `GET /api/users/{id}` | пользователь по id |
| | `POST /api/users` | регистрация |
| | `PUT /api/users/{id}` | изменить логин и почту |
| | `DELETE /api/users/{id}` | удалить |
| Модели техники | `GET /api/models?categoryPrefix=` | список, можно отфильтровать по категории |
| | `GET /api/models/{id}` | модель по id |
| | `POST /api/models` | создать модель |
| | `PUT /api/models/{id}` | изменить описание и тариф |
| | `DELETE /api/models/{id}` | удалить |
| Техника | `GET /api/equipment?categoryPrefix=&status=&condition=&name=` | поиск с фильтрами |
| | `GET /api/equipment/best?name=` | лучший свободный экземпляр модели |
| | `GET /api/equipment/{id}` | экземпляр по id |
| | `POST /api/equipment` | добавить экземпляр |
| | `PATCH /api/equipment/{id}/condition` | сменить состояние (с причиной) |
| | `DELETE /api/equipment/{id}` | удалить |
| | `GET /api/equipment/{id}/notes` | журнал заметок |
| | `POST /api/equipment/{id}/notes` | добавить заметку |
| Аренды | `GET /api/rentals?customerId=&equipmentId=&status=` | поиск с фильтрами |
| | `GET /api/rentals/{id}` | аренда по id |
| | `POST /api/rentals` | забронировать |
| | `POST /api/rentals/{id}/issue` | выдать технику |
| | `POST /api/rentals/{id}/return` | принять технику |
| | `PATCH /api/rentals/{id}/extend` | продлить |
| | `DELETE /api/rentals/{id}` | отменить бронь (только `BOOKED`) |
| | `POST /api/rentals/overdue-check?today=` | проверить просрочки в нескольких потоках |

## Структура

### `model`
Сущности JPA:
- `User` (абстрактный) — базовый пользователь, от него наследуются `AdminUser`, `ManagerUser`, `CustomerUser` (одна таблица, роль хранится в колонке `role`)
- `UserRole` — роль пользователя (`ADMIN`, `MANAGER`, `CUSTOMER`)
- `EquipmentCategory` — категория техники (справочник, ключ — префикс из трёх букв, хранит счётчик серийных номеров)
- `EquipmentModel` — модель техники: бренд, название, описание, тариф
- `Equipment` — экземпляр техники: модель, серийный номер, статус и состояние
- `EquipmentStatus`, `EquipmentCondition` — текущий статус и физическое состояние техники
- `EquipmentNote` — заметка о причине изменения состояния техники (журнал для аудита)
- `Rental` — запись об аренде: кто, что, на какой срок
- `RentalStatus` — статус аренды (`BOOKED`, `ACTIVE`, `RETURNED`, `OVERDUE`)

### `repository`
Интерфейсы Spring Data JPA. Фильтры строятся через `Specification`, связанные сущности для списков подгружаются одним запросом (`@EntityGraph`). Для бронирования и списания строка техники блокируется (`PESSIMISTIC_WRITE`).

### `service`
Бизнес-логика приложения:
- `EquipmentService` — модели и экземпляры техники, подбор лучшего доступного экземпляра, изменение состояния с обязательным обоснованием, заметки, серийные номера
- `UserService` — регистрация, изменение и удаление пользователей
- `RentalService` — бронирование, выдача, приём, продление и отмена аренды, проверка пересечения дат

### `concurrent`
`RentalOverdueProcessor` — многопоточный поиск просроченных аренд: список делится между потоками `OverdueChecker-N`, в лог пишется, какой поток что нашёл.

### `controller` и `dto`
REST-контроллеры и объекты запросов и ответов. `GlobalExceptionHandler` превращает исключения в ответы `400`, `404` и `409`. Транзакция открывается на контроллерах, потому что `open-in-view` выключен, а DTO читает ленивые связи.

### `config`
`OpenApiConfig` (описание Swagger), `ClockConfig` (часы вынесены в бин, чтобы в тестах подставлять фиксированную дату), `ApiDocs` (константы для Swagger-аннотаций).

## Тесты
Юнит-тесты для сущностей, сервисов, контроллеров и многопоточной обработки. В тестах нет подключения к базе: используется `@SpringBootTest` только с нужными классами, а репозитории подменяются через `@MockitoBean`. Контроллеры проверяются через MockMvc.

**Maven Wrapper** из корня проекта:
```
./mvnw test
```

**IntelliJ IDEA:** правой кнопкой на папку `src/test/java` → Run All Tests

JPQL-запросы и ограничения БД без базы не проверить, их проверяет демо (см. ниже).

## Демо
Приложение должно быть запущено. Скрипт проходит по всему API (создание, чтение с фильтрами, изменение, удаление и ожидаемые ошибки), даты считаются от сегодняшнего дня:
```
./demo.sh
```
`PAUSE=1 ./demo.sh` останавливается после каждого запроса, `HOST=http://... ./demo.sh` задаёт другой адрес. Те же запросы есть в `http/demo.http` для HTTP-клиента IntelliJ IDEA.

## Ограничения
- Пароль пока сохраняется в колонке `password_hash` как есть, хэширование и авторизация появятся в лабораторной про Spring Security. В ответах пароль не возвращается.
- Идентификаторы сотрудника и клиента сейчас передаются в теле запроса, после авторизации они будут браться из текущего пользователя.
